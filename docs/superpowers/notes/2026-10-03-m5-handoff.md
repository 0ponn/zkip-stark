# 2026-10-03: M5 handoff, commitment bound into the proof

**What changed.** The production certificate path now proves the fused
`merkle_predicate_batch1` circuit: public claim `[0, funIdx, threshold,
r0..r7, 1]` with the full 256-bit Blake3 root as eight little-endian u32
words, private witness = the 4-byte leaf and the Merkle path.
`ZkIpProtocol/FusedCircuit.lean` owns the merged toplevel, the lazily cached
`AiurSystem` (one build per process, replacing the per-request recompile), and
the encoders the six study tests used to copy. `generateSTARKProof` /
`verifySTARKProof` / `generateCertificateWithSTARK` take `(threshold, root,
leaf, path)` / `(threshold, root)` / `(ixon, predicate, attributeIndex)`.
`/generate` takes `attributeIndex` instead of `privateAttribute`, recomputes
the root from the attributes (a supplied `merkleRoot` must match), and shares
`generateFromJson` with the batch handler. `PredicateCircuit`, `CircuitABI`,
`toAiurBytecode`, the two tautological checks and `Optimization.lean` are
gone. Spec: `docs/superpowers/specs/2026-10-03-m5-merkle-binding-design.md`;
plan: `docs/superpowers/plans/2026-10-03-m5-merkle-binding.md`.

**What is verified.** `Tests/Validation/PredicateSoundness.lean` (23 checks,
exit 0): positive/negative/boundary predicate; no leak; threshold, commitment
and funIdx binding; u32 guards on both sides; certificate guards (range,
operator, index, client root); no mock certificate; API round trip with a
swapped commitment rejected; API 400s for `privateAttribute`, `>=`, huge
attribute, bad index, wrong root; 500 for a false predicate; depth 0, 5 (odd),
8 and 16. All 15 executables build; HashTests, STARKTests, ProveVerifyRoundtrip,
MerkleScheme, MerkleCircuitSingle/Path, MerklePredicate, BatchDisclosure,
MerkleNodeHashSpike exit 0. Timing at production parameters in
`docs/performance.md`: 260-320 ms prove, 21-24 ms verify, 4.77 MB proof, flat
from 1 to 1024 attributes.

**Final review (code-review agent at high effort, hermes-local lane).** Ten
findings; fixed in `51f5351`: operator not checked at verify (a relabelled
`<` verified), `parseIxon` silently dropping malformed attributes and
coercing bad root hex to "absent" (shifted `attributeIndex`, bypassed the
root check), unbounded batch size (now `maxBatchRequests = 16`, handler moved
into `Api.lean` so it is tested), stale API-reference signatures and CI grep,
and three simplifications (tautological `SecurityValidation`, `Advertisement`
stubs, four-way `evaluate` copy). Deferred: a false predicate is still a 500
(the prover API cannot yet distinguish "false" from "failed"); batch returns
200 with per-entry errors; the CI withdrawn-claims exclusion filter is loose.

**What is next.** K>1 batch disclosure through the HTTP API (the circuit
entries exist); binding attribute type/name into the leaf (today only the
value is committed); an `ApiTests` replacement for the JSON round trip;
the `isoc23Shim` lakefile target; REMEDIATION O3 (is Aiur's STARK
zero-knowledge).

**What is risky.** Hiding is still unproven (O3). `fusedSystem` is an
`IO.Ref` cache: two first callers on different threads could both build the
system (idempotent, wasteful, not unsafe). The 4.77 MB proof is the same at
every depth, so proof size is dominated by the Blake3 gadget rows; batching
is the only lever left on size. `lake-manifest.json` is gitignored, so the
ix pin lives only in `lakefile.lean` (by sha, to the `0ponn/ix` fork).
