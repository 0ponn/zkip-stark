# Performance

## Measured CPU Baseline

The only real performance numbers this project has: a no-GPU wall-clock
baseline captured with `Tests/Validation/CpuBaseline.lean`
(`lake exe Tests.Validation.CpuBaseline`). Full data, methodology, and raw
runs: `docs/superpowers/notes/2026-07-18-cpu-baseline.md`.

- **Machine**: Intel(R) Core(TM) i5-11600K @ 3.90GHz, 12 cores (`nproc`), 31 GiB RAM, no GPU.
- **Circuit**: 3-attribute `Ixon` (`performance`, `security`, `efficiency`), Merkle-committed, single `PredicateCircuit`, ~22k estimated constraints.
- **Median proving time**: 415-491 ms across two runs.
- **Verify time**: 42-49 ms.
- Proofs generated by the harness verify successfully (`verifySTARKProof` returns `true`).

There is no hardware bottleneck here. The system had never been built or
benchmarked before this measurement — there was nothing to accelerate away.
Earlier drafts of this document described a "NoCap hardware UNAVAILABLE —
CRITICAL PERFORMANCE BOTTLENECK" that does not reflect reality: the prover
does not use NoCap or Poseidon hardware at all, and CPU proving is already
sub-second for this circuit size.

## The Prover's Real Hash: Blake3

The proving stack is Ix/Aiur -> multi-stark -> Plonky3, over the Goldilocks
field. `multi-stark`'s MMCS (`multi-stark/src/types.rs`) is configured as
`MerkleTreeMmcs<Val, u8, SerializingHasher<Blake3>, Blake3CompressionFunction, 2, 32>`
— **Blake3**, not Poseidon. The application-layer Merkle commitment in
`CoreTypes.lean` also uses Blake3 (`Address.blake3`), matching the prover.
`NoCapFFI.lean` is a software-only stub (`HardwareCtx.create` always returns
`none`) that is not on this hot path — it is a red herring for proving
performance and is marked vestigial in the source.

## GPU Acceleration (Planned, Not Done)

GPU work is planned at the Plonky3 `TwoAdicFriPcs` trait seam — new types
implementing `TwoAdicSubgroupDft` and `Mmcs` with CUDA behind FFI, starting
with the NTT, swapped into `multi-stark`'s type aliases. This does not touch
Aiur or the constraint system, and it has nothing to do with NoCap or
Poseidon. See `docs/superpowers/specs/2026-07-18-gpu-proving-backend-design.md`
for the full design. The CPU baseline above is the number any GPU claim has
to beat.

## Proof Size

Recursive proof composition is designed to keep proof size constant across
state transitions, via the verifier circuits in `RecursiveProofs.lean` /
`FullRecursiveVerification.lean`. This has not been independently measured
on the compiling path — treat any specific KB figure as unverified until it
is.

## Optimization Techniques

### Batching
Multiple attribute checks in a single STARK proof reduce per-attribute overhead.

### Recursive Proofs
State transitions via verifier circuits; present in the library, not part
of the currently-measured hot path.

### String Matching
ASCII character packing into field elements (`StringMatchOptimization.lean`)
— this module does not currently compile and is unverified.

### Boolean Logic Arithmetization
Non-zero = True for efficient OR-gates:
- **Method**: Linear combinations instead of multiplicative gates
- **Benefit**: Reduced constraint count for policy evaluation
